# Semantic Version Bumper

Parses the current semantic version from a `VERSION` file **or** `package.json`,
inspects [Conventional Commit](https://www.conventionalcommits.org/) messages to
decide the next version, writes the new version back, prepends a
[Keep a Changelog](https://keepachangelog.com/) entry, and prints the result.

| Commit kind | Example | Bump |
| --- | --- | --- |
| Feature | `feat: add login` | **minor** |
| Fix / perf | `fix: ...`, `perf: ...` | **patch** |
| Breaking | `feat!: ...` or a `BREAKING CHANGE:` footer | **major** |
| Anything else | `docs:`, `chore:`, `test:` ... | none (version unchanged) |

The highest-precedence bump across all commits wins; `major` > `minor` > `patch`.
No release-worthy commits is a graceful no-op, not an error.

## Files

| Path | Purpose |
| --- | --- |
| `version_bumper.py` | The bumper — pure-stdlib Python 3, small testable functions + a thin CLI. |
| `tests/test_version_bumper.py` | Red/green TDD unit tests for the pure logic. |
| `tests/test_workflow.py` | Static workflow-structure tests + `actionlint` check. |
| `tests/test_act_integration.py` | Runs the workflow end-to-end through `act` and asserts exact versions. |
| `fixtures/<scenario>/` | Mock commit-log fixtures (`commits.txt` + `VERSION`/`package.json`). |
| `.github/workflows/semantic-version-bumper.yml` | The CI/CD pipeline. |
| `VERSION`, `commits.txt`, `CHANGELOG.md` | Repo-level inputs used by the workflow's `release` job. |
| `act-result.txt` | Captured output of the `act` run (generated by the integration test). |

## Usage

```bash
# Dry run: just compute and print the next version.
python3 version_bumper.py --version-file VERSION --commits commits.txt

# Apply: write the new version + prepend a changelog entry.
python3 version_bumper.py --version-file VERSION --commits commits.txt --write
```

Output is machine-readable:

```
CURRENT_VERSION=1.0.0
BUMP_TYPE=minor
NEW_VERSION=1.1.0
COMMIT_COUNT=3
```

When run inside GitHub Actions the script also writes `current_version`,
`new_version`, `bump_type`, and `changed` to `$GITHUB_OUTPUT` and a summary
table to `$GITHUB_STEP_SUMMARY`.

## TDD methodology

Built strictly red → green → refactor: each function in `version_bumper.py` was
driven by a failing unit test first (see `tests/test_version_bumper.py`). The
fast unit tests are the development scaffold; the **authoritative** behavioural
check runs every scenario *through the GitHub Actions workflow* via `act`
(`tests/test_act_integration.py`), which captures `act-result.txt` and asserts
the exact next version for each fixture.

## The workflow

`.github/workflows/semantic-version-bumper.yml` has two jobs:

1. **`validate`** — a build matrix over the five fixture scenarios. Each runs the
   bumper and prints an exact, self-identifying `RESULT scenario=<name>
   new_version=<v>` line. This is the release-logic regression suite.
2. **`release`** — depends on `validate`; runs the bumper against the repo's own
   `VERSION` + `commits.txt`, writes the bump + changelog, and exposes the new
   version as a step output / job summary (the real release action).

It uses `actions/checkout@v4`, least-privilege `permissions` (the release job
opts up to `contents: write`), and needs no external services or secrets — the
optional tag/publish step is guarded off by default so it runs cleanly in `act`.

## Running everything

```bash
python3 -m pytest tests/ -v        # all unit + structure + act integration tests
actionlint .github/workflows/semantic-version-bumper.yml
```
