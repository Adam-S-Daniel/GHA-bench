# Semantic Version Bumper

A small Bash tool that reads a semantic version, decides the next version from
[Conventional Commits](https://www.conventionalcommits.org/), updates the
version file, writes a changelog entry, and prints the new version. It ships
with a full bats test suite and a GitHub Actions workflow that runs end-to-end
in an isolated container (validated locally with [`act`](https://github.com/nektos/act)).

## Bump rules (Conventional Commits → SemVer)

| Commit signal                                   | Bump   |
| ----------------------------------------------- | ------ |
| `feat!: …`, `fix!: …`, or a `BREAKING CHANGE` footer | major  |
| `feat: …` / `feat(scope): …`                    | minor  |
| `fix: …` / `fix(scope): …`                      | patch  |
| anything else (chore, docs, refactor, …)        | none   |

Precedence is highest-wins: any breaking change ⇒ major, else any feat ⇒ minor,
else any fix ⇒ patch, else no bump (files are left untouched).

## Layout

| Path                                          | Purpose                                                        |
| --------------------------------------------- | ------------------------------------------------------------- |
| `semantic-version-bumper.sh`                  | The tool. Source-safe: sourcing it only defines `svb_*` funcs. |
| `VERSION`, `commits.txt`                      | Default inputs the workflow runs on (overridden per test case).|
| `fixtures/`                                   | Mock commit logs (feat / fix / breaking / mixed / none) + a sample `package.json`. |
| `test/version_bumper.bats`                    | TDD unit tests for every function and the CLI (49 tests).      |
| `test/workflow_structure.bats`                | Structural tests of the workflow YAML + `actionlint` (15 tests).|
| `test/integration_act.bats`                   | End-to-end tests through the workflow via `act` (3 cases).     |
| `test/wf_query.py`                            | Helper that normalises the workflow YAML to JSON for jq.       |
| `.github/workflows/semantic-version-bumper.yml` | The CI pipeline.                                             |
| `act-result.txt`                              | Captured output of every `act` run (generated by the act suite).|

## Usage

```bash
# Plain VERSION file, commits read from a file (one header per line):
./semantic-version-bumper.sh \
  --version-file VERSION \
  --commits-file fixtures/commits-feat.txt \
  --changelog-file CHANGELOG.md

# package.json is auto-detected and only its "version" field is rewritten:
./semantic-version-bumper.sh --version-file package.json --commits-file commits.txt

# No --commits-file => commit subjects are read from `git log` (since the last tag).
./semantic-version-bumper.sh --version-file VERSION

# Preview only, change nothing:
./semantic-version-bumper.sh --version-file VERSION --commits-file commits.txt --dry-run
```

The script prints a human summary plus a machine-readable `NEW_VERSION=<v>` line,
and when run inside GitHub Actions it also writes `new_version` / `bump_type`
step outputs to `$GITHUB_OUTPUT`. `--help` documents all options.

## Testing

Built red/green/refactor with [bats-core](https://github.com/bats-core/bats-core).

```bash
./run-tests.sh         # lint + unit + workflow-structure suites (fast)
./run-tests.sh --act   # also run the act integration suite (Docker, slower)

# or directly:
bats test/version_bumper.bats test/workflow_structure.bats
bats test/integration_act.bats        # spins containers via act
```

The script passes `bash -n`, `shellcheck`, and the workflow passes `actionlint`.

## CI pipeline

`.github/workflows/semantic-version-bumper.yml` triggers on `push`,
`pull_request`, a weekly `schedule`, and `workflow_dispatch` (with
`version_file` / `commits_file` / `release_date` inputs). It uses least-privilege
`contents: read` permissions and two jobs:

1. **bump** — checks out the repo, validates the script with `bash -n`, runs the
   bumper against the version/commits files, prints the changelog, and exposes
   `new_version` / `bump_type` as job outputs.
2. **report** — `needs: bump`; consumes those outputs and echoes the result,
   demonstrating cross-job output passing.

Every step is self-contained (no external services or secrets), so it runs
unchanged under `act`.
