# Test Results Aggregator

Parses test result files (JUnit XML and JSON), aggregates them across a matrix
build, computes totals, flags flaky tests, and emits a Markdown summary suitable
for a GitHub Actions job summary (`$GITHUB_STEP_SUMMARY`).

## Why Python

The task needs robust XML and JSON parsing plus tidy Markdown generation. Python's
standard library (`xml.etree.ElementTree`, `json`, `argparse`) covers all of it
with zero third-party dependencies, so the script runs unchanged in a bare CI
container with no install step.

## Layout

| Path | Purpose |
| --- | --- |
| `aggregate.py` | The aggregator script (CLI + importable functions). |
| `tests/test_aggregate.py` | Fast unit tests (TDD red/green) for the parsing / aggregation / rendering logic. |
| `tests/test_workflow_act.py` | End-to-end tests that run the workflow in Docker via `act`, plus workflow-structure tests. |
| `fixtures/cases/<case>/` | Sample JUnit XML / JSON result files for each test case. |
| `test-results/` | Default directory the workflow reads (sample data for normal pushes). |
| `.github/workflows/test-results-aggregator.yml` | The CI workflow. |
| `act-result.txt` | Captured output of running the workflow under `act` (generated by the test suite). |

## Usage

```bash
# Aggregate every .xml/.json file in a directory and print a Markdown summary.
python3 aggregate.py test-results

# In CI: also write the summary to the job summary and metrics to job outputs.
python3 aggregate.py test-results \
    --summary "$GITHUB_STEP_SUMMARY" \
    --github-output "$GITHUB_OUTPUT"

# Optionally make the step fail the build when any test failed or errored.
python3 aggregate.py test-results --fail-on-failures
```

The script prints the Markdown summary followed by a machine-readable metrics
block between `=== AGGREGATE METRICS ===` / `=== END METRICS ===` markers so a
CI step (or the test harness) can assert on exact values.

## Supported input formats

**JUnit XML** — either a `<testsuites>` wrapper or a single `<testsuite>`. Each
`<testcase>` is classified by its child element: `<failure>` -> failed,
`<error>` -> error, `<skipped>` -> skipped, otherwise passed. The test identity
is `classname.name`.

**JSON** — an object with a `tests` array, or a bare array. Each entry is
`{"name", "status", "duration"|"time"}`. Common status spellings (`pass`,
`fail`, `skip`, ...) are normalised.

## Flaky detection

A test (identified by its stable `classname.name`) is **flaky** when it both
passed in at least one run and failed/errored in at least one other run. An
`error` counts as a failure for flakiness; `skipped` never counts as a pass or a
fail.

## Testing

```bash
python3 -m pytest tests/ -v
```

- The unit tests drive the implementation via TDD and run in milliseconds.
- The `act` tests build a throwaway git repo per case, run `act push --rm`
  against the workflow inside Docker, append each run's output to
  `act-result.txt`, and assert the workflow produced the EXACT expected totals
  and flaky tests (and that every job reports `Job succeeded`).

> The custom act image is local-only, so the harness runs act with `--pull=false`.
